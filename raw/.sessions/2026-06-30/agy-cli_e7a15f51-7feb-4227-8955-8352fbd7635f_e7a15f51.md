```text
/
├── .agent/              # Configuration and formal specs (e.g., design.md, tasks.md)

├── skills/              # Reusable "expertise" directories (SKILL.md + optional scripts/refs)
```

### 2. Key Components Explained
*   **Agents:** Autonomous sub-processes designed for specific tasks (e.g., `researcher-agent`, `coder-agent`). They often contain their own prompt context, tool access, and configuration, allowing them to operate independently and return results to a parent or orchestrator agent.
*   **Skills:** These are "quasi-multi-agent" building blocks. Instead of flat files, skills are typically directories containing a `SKILL.md` (the "instruction" set) along with optional resources like scripts, templates, or documentation. Agents load these on-demand, which helps keep the active context window lean and focused.
*   **Plugins:** These act as the distribution unit. A plugin is essentially a bundle of agents, skills, and MCP (Model Context Protocol) servers. They allow you to share or install modular, specialized capabilities (e.g., "python-development-plugin") without manually managing every individual file.

### 3. Best Practices for Organization
*   **Progressive Context Loading:** Do not dump all instructions into the root. By using a directory-based structure (like the one supported by Claude Code or Codex), the framework can "discover" skills by name/description and only read the full `SKILL.md` when the agent actually needs that capability.
*   **Decoupled Logic:** Separate your "governance" (orchestration/workflow logic) from the "execution" (the tools and skills the agents actually use). This makes it easier to test agents individually before integrating them into a complex, multi-step flow.
*   **Workspace Separation:** For true multi-agent setups, avoid nesting workspace configurations too deeply if the framework requires a root-level `config` or `instructions` file. If an agent needs a distinct "personality" or toolset, consider giving it its own workspace directory with its own configuration files.
*   **Documentation as Code:** Use `docs/` folders for architecture, ERDs, and decision logs. Treat this documentation as a primary input for your agents; if an agent is confused, it should be able to "read the manual" within your repository to understand the project's rules and standards.

### 4. When to Use Which Architecture
*   **Start Simple:** Begin with a single agent and well-defined tools. Only graduate to multi-agent architectures (like hierarchical, sequential, or swarm patterns) when you reach the limits of a single agent's context window or reasoning capacity.
*   **Orchestration:** Use orchestrators (e.g., `LoopAgent` or `Supervisor`) to manage handoffs between specialized agents. This delegation model is far more reliable for production systems than attempting a "monolithic" agent approach.
