# Design Spec Schema — Design Spec JSON Format Definition

This document defines the schema for the JSON spec generated by the tds-design skill.

## Step 1: Proposal Format

```typescript
interface DesignProposal {
  taskId: string;          // Screen identifier (e.g. "basicInfo-form")
  page: string;            // Route path (e.g. "/employer/contracts/new")
  step?: string;           // Wizard step name (omit if none)
  proposals: ProposalItem[];
}

interface ProposalItem {
  id: string;              // "A" ~ "E"
  pattern: LayoutPattern;  // Layout pattern
  components: string[];    // List of TDS components to use
  layout: LayoutType;     // Layout type
  description: string;    // One-line description
  estimatedTokens: number; // Estimated token count for rendering
}

type LayoutPattern = "bottom-sheet" | "full-page" | "list-detail" | "modal" | "funnel";
type LayoutType = "stack" | "scroll" | "grid" | "inline-expand" | "center" | "funnel";
```

## Step 2: Full Design Spec Format

```typescript
interface DesignSpec {
  taskId: string;           // Same as Step 1
  selectedId: string;       // Selected proposal ID

  intent: string;           // Intent and purpose of this design (1-2 sentences)
  uxEvaluation: UxEvaluation; // Mandatory UX Evaluation based on theories

  componentTree: ComponentNode;  // Component tree (recursive structure)

  stateBindings: Record<string, StateBinding>;  // State bindings

  interactions: Interaction[];  // User interaction definitions

  referenceFiles: string[];     // Paths to existing code files to modify

  rejectedAlternatives: RejectedAlternative[];  // Rejected proposals and their reasons
}

interface UxEvaluation {
  philosophyAndIntent: string; // The core design philosophy and underlying intent (UX theory grounded)
  expectedImpact: string;      // Expected usability/time-to-complete impact
  pros: UxEvaluationItem[];    // Pros mapped to specific UX theories
  cons: UxEvaluationItem[];    // Cons mapped to specific UX theories
}

interface UxEvaluationItem {
  theory: string;              // Named UX theory (e.g. "Hick's Law", "Fitts's Law", "Jakob's Law")
  rationale: string;           // Usability rationale linking the design choice to the theory
}

interface ComponentNode {
  component: string;       // TDS component name or "div.container"
  props?: Record<string, any>;     // Component props
  bindTo?: string;         // State binding key (key in stateBindings)
  action?: string;         // Interaction key (matches interactions trigger)
  actionLabel?: string;    // Button or similar text
  children?: ComponentNode[];
}

interface StateBinding {
  from: string;            // State source (e.g. "useContractForm().form.worker_name")
  setBy?: string;          // State setter (e.g. "useContractForm().handleChange")
}

interface Interaction {
  trigger: string;         // Trigger (e.g. "Click Button (Next)")
  action: string;          // Action to execute (e.g. "validateStep → next step")
  errorHandling?: string;  // Error handling (e.g. "Show error on TextField if invalid")
}

interface RejectedAlternative {
  id: string;              // Rejected proposal ID
  pattern: LayoutPattern;  // Layout pattern
  reason: string;          // Rejection reason
}
```

## Step 3: Agent Delivery Format

When delivering to the implementation agent, include the full DesignSpec JSON in `assignment`:

```
Modify according to the following design spec:
- Target files: {referenceFiles}
- Spec: {DesignSpec JSON}
- Import TDS components from @toss/tds-mobile
- Follow existing code patterns
```

## Storage Paths

- Proposals: `server/ux-test-sessions/design-{timestamp}.json`
- Spec: `server/ux-test-sessions/design-{timestamp}-spec.json`

## History Preservation

Multiple proposals/specs can be generated for the same taskId.
They are distinguished by timestamp, and previous versions are not overwritten.
